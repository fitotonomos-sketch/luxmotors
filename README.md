# لوکس موتورز — راهنمای فنی، استقرار و انتقال میزبانی

این پروژه یک وب‌سایت فارسی راست‌چین برای لوکس موتورز است. رابط عمومی با **Astro** ساخته شده و بخش‌هایی که دادهٔ زنده، ورود مدیر یا فهرست خودرو دارند با **React** در مرورگر اجرا می‌شوند. داده‌ها، احراز هویت و فایل‌های رسانه به **Supabase** متصل‌اند. استقرار فعلی B12 شامل چند اتصال مخصوص B12 است؛ انتقال فایل‌های فرانت‌اند به هاست دیگر به‌تنهایی این سرویس‌ها را منتقل نمی‌کند.

> این راهنما دربارهٔ معماری و تنظیمات موردنیاز است، نه تضمین سازگاری یک هاست مشخص. پیش از جابه‌جایی، آدرس دامنه، فرم‌ها، احراز هویت، داده‌ها، فایل‌های رسانه و قوانین امنیتی را در محیط آزمایشی بررسی کنید. کد این پروژه به‌تنهایی شامل نسخهٔ پشتیبان داده یا فایل‌های Supabase نیست.

## اجزای اصلی

- `src/pages/` — صفحات استاتیک Astro و مسیرهای سایت.
- `src/components/` — اجزای Astro و React؛ پنل ادمین در `AdminPanel.tsx`، `AdminStudio.tsx`، `AdminOrders.tsx`، `AdminSettings.tsx` و `AdminUsers.tsx` است.
- `src/styles/global.css` — CSS سایت و پنل.
- `src/lib/supabase.ts` — کلاینت عمومی Supabase؛ فقط از متغیرهای `PUBLIC_*` استفاده می‌کند.
- `supabase/migrations/` — ساختار پایگاه داده، RLS، نقش‌ها و داده‌های اولیه.
- `supabase/functions/public-sitemap/` — نقشهٔ سایت زندهٔ خودروها و دسته‌بندی‌های منتشرشده.
- `src/b12Context.json` — شناسه و تنظیمات لازم برای اتصال‌های محیط B12؛ این فایل جایگزین تنظیمات محیط مقصد نیست.

## ساخت و خروجی

اسکریپت ساخت تعریف‌شده در `package.json`، `build` است و خروجی Astro در پوشهٔ `dist/` قرار می‌گیرد. در پنل ساخت هاست، نسخهٔ سازگار Node.js را مطابق نیاز Astro 5 انتخاب، وابستگی‌ها را از `pnpm-lock.yaml` نصب و دستور build را اجرا کنید؛ پوشهٔ خروجی را `dist` قرار دهید. برای پیش‌نمایش محلی، اسکریپت `preview` در `package.json` در دسترس است. هاست باید فایل‌های مسیرهای عمیق را درست سرو کند و برای `robots.txt`، `sitemap-index.xml` و فایل‌های عمومی، پاسخ مناسب بدهد.

سایت عمدتاً استاتیک ساخته می‌شود. درخواست‌ها به Supabase از مرورگر انجام می‌شوند؛ مقدار محرمانهٔ سرویس‌دهنده نباید در JavaScript، HTML یا متغیر دارای پیشوند `PUBLIC_` قرار گیرد. هیچ کلید service-role در این مخزن قرار داده نشده است و عمداً نباید به مرورگر اضافه شود.

## متغیرهای محیطی

این متغیرها را در **تنظیمات build/deploy هاست** تعریف کنید، نه در کد یا فایل عمومی:

| نام | کاربرد |
| --- | --- |
| `PUBLIC_SITE_URL` | نشانی نهایی سایت با `https://`، بدون مسیر صفحه؛ مبنای sitemap، canonical اولیه و تنظیمات دامنهٔ استقرار. برای پیش‌نمایش B12 خالی بماند تا مقدار `src/b12Context.json` استفاده شود. |
| `PUBLIC_SUPABASE_URL` | URL پروژهٔ Supabase که رابط سایت از مرورگر به آن متصل می‌شود. |
| `PUBLIC_SUPABASE_KEY` | کلید publishable عمومی Supabase؛ این کلید به‌خودی‌خود نباید دسترسی نوشتن را باز کند و امنیت واقعی باید با RLS برقرار شود. |
| `PUBLIC_AUTH_DOMAIN` | نام میزبان مقصدی که پیوندهای تأیید ایمیل و بازیابی رمز به آن برمی‌گردند؛ فقط نام میزبان، بدون `https://`. |
| `PUBLIC_IS_PREVIEW` | فقط برای deploy آزمایشی مقدار `true` بگذارید تا `robots.txt` کل سایت را از ایندکس دور نگه دارد. برای سایت عمومی آن را `false` یا خالی کنید. |
| `PUBLIC_ENABLE_B12_INTEGRATIONS` | در سایت B12 خالی/`true` بماند. در هاست مستقل، اتصال‌های ردیابی و reCAPTCHA مربوط به B12 به‌طور پیش‌فرض غیرفعال می‌شوند؛ `true` فقط زمانی بگذارید که آگاهانه هنوز از سرویس‌های B12 استفاده می‌کنید. |
| `PUBLIC_ENABLE_B12_PREVIEW` | به‌ندرت لازم است؛ فقط برای پل ارتباطی پیش‌نمایش داخل ویرایشگر B12 مقدار `true` بدهید. در میزبانی مستقل خالی بماند. |

مقادیر این پروژه برای B12 از قبل در محیط build تأمین می‌شوند؛ انتقال به مقصد دیگر به مقادیر همان مقصد نیاز دارد. مقادیر خصوصی، گذرواژه، توکن سرویس‌دهنده یا کلید service-role را در README، مخزن کد یا `PUBLIC_*` قرار ندهید.

## هاست و CDN: چه چیزی به هم متصل می‌شود؟

**هاست** فایل‌های ساخته‌شدهٔ `dist/` را با HTTPS ارائه می‌کند. **CDN** فایل‌های استاتیک مثل CSS، JavaScript، فونت و تصاویر را از نقاط نزدیک‌تر به بازدیدکننده cache و تحویل می‌دهد. اگر CDN داخل هاست فعال است، معمولاً لازم نیست URLها را دستی در همهٔ صفحات عوض کنید؛ DNS دامنه را طبق راهنمای همان ارائه‌دهنده به هاست/CDN وصل کنید و مطمئن شوید فایل‌های استاتیک و مسیرهای Astro از همان origin به‌درستی پاسخ می‌گیرند.

ترتیب پیشنهادی انتقال:

1. مقصد را با دامنهٔ آزمایشی HTTPS بالا بیاورید و `PUBLIC_SITE_URL` را به همان دامنه تنظیم کنید.
2. دامنهٔ مقصد را برای پیوندهای ورود/تأیید در تنظیمات مجاز احراز هویت همان سرویس Supabase ثبت کنید؛ `PUBLIC_AUTH_DOMAIN` نیز باید دقیقاً به همین میزبان اشاره کند.
3. deploy آزمایشی انجام دهید و مسیرهای `/`، `/store`، `/products?slug=...`، `/categories`، `/purchase-guide`، `/modiriyatfrosh` و مسیرهای مدیریت را بررسی کنید.
4. پس از اتصال دامنهٔ اصلی، `PUBLIC_SITE_URL` را به دامنهٔ اصلی تغییر دهید، `PUBLIC_IS_PREVIEW` را بردارید یا `false` کنید، build تازه بگیرید و sitemap/robots را دوباره بررسی کنید.
5. اگر CDN جدا از هاست دارید، cache فایل‌های نام‌دار با hash را طولانی نگه دارید؛ برای `robots.txt`، `sitemap-index.xml` و صفحات HTML cache کوتاه‌تر یا purge پس از deploy در نظر بگیرید. از cache کردن پاسخ‌های احراز هویت یا داده‌های مدیریتی در CDN عمومی خودداری کنید.

هنگام انتقال، مسیر Supabase ثابت نمی‌ماند مگر همان پروژه را نگه دارید. جابه‌جایی هاست، خودکار دیتابیس، حساب‌ها، سفارش‌ها یا Storage را منتقل نمی‌کند. هر مهاجرت پایگاه داده باید با حفظ ترتیب اجرا شود؛ RLS و policyها را از روی migrationها بازبینی و در مقصد آزمایش کنید. اگر مقصد backend دیگری است، client، احراز هویت، جداول، RLS، Storage، سفارش‌ها و Edge Function نقشهٔ سایت باید جداگانه بازپیاده‌سازی و آزمایش شوند؛ صرفاً جایگزین‌کردن URL در HTML کافی نیست.

## فایل‌های رسانه و CDN تصاویر

در وضعیت فعلی، تصاویر آپلودشدهٔ پنل از Storage عمومی `site-media` در Supabase URL می‌گیرند. تصویر قهرمان، پس‌زمینهٔ ورود و favicon اولیه روی `cdn.b12.io` هستند و Google Fonts نیز از `fonts.googleapis.com` بارگیری می‌شود. URLهای B12 وابستگی به سرویس B12 هستند؛ جابه‌جایی کد آن‌ها را به CDN مقصد منتقل نمی‌کند. `src/components/B12Link.astro` نیز در Footer استفاده می‌شود و اکنون پیوند placeholder معیوب `https://www.?utm_...` و برچسب Alpha دارد؛ پیش از انتشار مستقل باید مقصد درست آن از مالک تأیید شود.

برای انتقال کامل رسانه، فایل‌های مجاز را با حفظ نام/مسیر یا با نام‌گذاری پایدار به Storage/CDN جدید کپی کنید، نشانی‌های ثبت‌شده در `site_content`, `products`, `banners` و `media_assets` را به مسیر مقصد تبدیل کنید، و مجوزهای خواندن/آپلود را آزمایش کنید. نشانی‌های فایل را فقط پس از اطمینان از کپی کامل عوض کنید. مقصد تصاویر باید HTTPS، `Content-Type` مناسب و CORS لازم برای خواندن از دامنهٔ سایت داشته باشد. فایل‌های لازم برای SEO مانند تصویر OG را نیز انتقال دهید. URLهای تکراری B12 در CSS/صفحات را با تصاویر منتقل‌شده جایگزین کنید یا عمداً در دسترس نگه دارید.

## فرم‌ها و اتصال‌های مخصوص B12

فرم‌هایی که `data-form-id` دارند به endpoint فرم B12 ارسال می‌شوند (`src/lib/forms.ts`). این ارسال شامل سرویس B12 و reCAPTCHA تنظیم‌شده برای همان محیط است؛ انتقال ظاهر سایت، ارسال فرم را به یک هاست یا CRM دیگر منتقل نمی‌کند. پیش از غیرفعال‌کردن اتصال‌های B12، فرم‌ها را به سامانهٔ دریافت فرم مقصد منتقل کنید و ارسال واقعی، پیام موفقیت/خطا، ضداسپم و حریم خصوصی را تست کنید. `PUBLIC_ENABLE_B12_INTEGRATIONS=true` فقط اتصال‌های ردیابی/reCAPTCHA B12 را نگه می‌دارد و به‌تنهایی endpoint فرم را به مقصد جدید تغییر نمی‌دهد.

بخش ترافیک B12 در `RequiredB12FooterScripts.astro` اختیاری شده است و برای deploy مستقل با `PUBLIC_SITE_URL` تنظیم‌شده اجرا نمی‌شود، مگر آن را صریحاً فعال کنید. پل preview در `RequiredB12HeadScripts.astro` هم به‌طور پیش‌فرض برای سایت مستقل خاموش است. با این حال `__CLIENT_UID__`/`__PRODUCT_URL__` از `b12Context.json` و endpoint فرم B12 در `src/lib/forms.ts` هنوز اتصال‌های باقی‌مانده‌اند. reCAPTCHA از Google است و site key فعلی hard-coded و به domain registration وابسته است؛ انتقال فرم به endpoint جدید باید reCAPTCHA متناسب با مقصد را نیز جایگزین کند. هیچ ادعایی دربارهٔ انتقال تاریخچهٔ analytics یا فرم‌های B12 در این repo وجود ندارد.

## سئو: معماری واقعی و محدودیت HTML اولیه

- متای عادی صفحات در Astro layout/page تعریف می‌شود؛ تنظیمات عمومی SEO در `site_content` و فیلدهای محصول/دسته در جداول ثبت‌اند.
- `PublicBrand.tsx` متادیتای محصول و دسته، canonical، Open Graph، Twitter Card و JSON-LD را پس از اجرای JavaScript در مرورگر از Supabase دریافت و تزریق می‌کند. بنابراین این داده‌ها در HTML اولیهٔ استاتیک نیستند.
- بازبینی Astro نشان داد خروجی static است و `src/pages/products/[slug].astro` به‌علت `getStaticPaths()` خالی هیچ صفحهٔ محصولی تولید نمی‌کند. لینک‌های واقعی جزئیات از query مانند `/products?slug=...` استفاده می‌کنند؛ URL اختصاصی `/products/{slug}` هنوز وجود ندارد.
- در این پروژه راهنمای اجرایی Supabase، همهٔ queryها را client-side الزامی می‌کند و SSR، server fetch در Astro frontmatter و routeهای دیتابیس‌محور را منع می‌کند. به همین دلیل SSR یا دریافت فهرست live در build پیاده‌سازی نشد و از داده‌های نمونه برای تولید صفحهٔ نادرست/stale استفاده نشد. نتیجه: crawler بدون اجرای JS ممکن است متای عمومی ببیند، نه متای اختصاصی محصول/دسته. تحقق الزام HTML اولیه نیازمند تصویب و تغییر این قید معماری است: pipeline مجاز برای build از فهرست واقعی منتشرشده، یا runtime/server جداگانه با حفظ RLS؛ service-role هرگز نباید به مرورگر برسد.
- JSON-LD کلاینتی مقدار قیمت تومانی را برای `IRR` به ریال تبدیل و موجودی را به `InStock`/`OutOfStock` نگاشت می‌کند. Sitemap پویا فقط محصول منتشرشده با `stock > 0` و دستهٔ منتشرشده را می‌گیرد؛ ردیف حذف‌شده/پیش‌نویس از query خارج است.
- Sitemap استاتیک Astro از `PUBLIC_SITE_URL` یا زمینهٔ B12 ساخته می‌شود. `robots.txt` در preview همه‌چیز را مسدود و در production مسیرهای پنل، پرداخت و احراز هویت را مسدود می‌کند. تابع sitemap با کلید عمومی و RLS کار می‌کند و هنگام انتقال Supabase باید در مقصد deploy شود.
- مقدار `canonical_url` دستی باید URL HTTPS معتبر و متعلق به دامنهٔ canonical باشد؛ دامنهٔ اشتباه می‌تواند ایندکس را منحرف کند.

Migration `20261102100000_enforce_scoped_admin_updates.sql` لایهٔ سمت‌سرور را تقویت می‌کند: triggerهای DB برای زیرمدیر SEO فقط ستون‌های SEO محصول/دسته را می‌پذیرند؛ مدیر سفارش فقط وضعیت سفارش/پرداخت را تغییر می‌دهد؛ مدیر رسانه فقط مسیرهای لوگو، آیکون، OG و قهرمان را تغییر می‌دهد؛ مدیر تنظیمات فقط ستون‌های تنظیمات پرداخت را تغییر می‌دهد؛ و SEO نمی‌تواند دسته ایجاد یا حذف کند. Migration `20261103100000_main_admin_delete_orders.sql` تابع `delete_order` را اضافه می‌کند: فقط مدیر اصلی می‌تواند آن را فراخوانی کند، اقلام و سفارش در یک تراکنش پاک می‌شوند و شماره سفارش در ممیزی نگهداری می‌شود. درج مستقیم در `audit_logs` از کلاینت بسته شده و رویداد حذف سفارش نیز از تابع دیتابیس ثبت می‌شود. RLS/trigger مرجع امنیت است؛ تست نفوذ یا تست چند حساب واقعی در این محیط انجام نشده. نقش قدیمی `administrator` دسترسی گسترده دارد، به‌جز مدیریت مدیران و مشاهده ممیزی؛ `subadmin` فقط مجوزهای ذخیره‌شده در `admins.permissions` را دارد. حساب‌ها از Auth/RLS استفاده می‌کنند و رمزها به‌صورت متن در سایت ذخیره نمی‌شوند. هیچ service-role در مرورگر نیست. فایل‌ها Auth user را منتقل نمی‌کنند.

## محدودیت‌های انتقالی که باید قبل از انتشار حل شوند

- اتصال به B12 برای ثبت فرم‌ها، ابزار پیش‌نمایش و برخی تصاویر می‌تواند پس از انتقال باقی بماند یا از کار بیفتد؛ مطابق بخش فرم‌ها و رسانه تعیین تکلیف کنید.
- ویژگی‌های فروشگاه و سفارش به Supabase وابسته‌اند؛ اگر Supabase باقی نمی‌ماند باید backend جایگزین شود. فایل‌های عمومی به‌تنهایی فروشگاه عملیاتی نیستند.
- HTML اختصاصی محصول/دسته و URLهای path-based هنوز وجود ندارد؛ محدودیت Supabase پروژه SSR و build-time DB fetch را منع می‌کند. رفع آن نیازمند تصویب تغییر معماری و حل امن دسترسی داده در مقصد است.
- بازنویسی مسیرهای query مانند `/products?slug=x` توسط اکثر هاست‌های static بدون تنظیم خاص لازم نیست، چون درخواست به `/products` می‌رود؛ با این حال تمام صفحات مستقیم و refresh مرورگر را روی میزبان نهایی تست کنید.
- پیش از DNS نهایی، canonical، `robots.txt`، sitemap، favicon، CORS، ایمیل تأیید، reset-password، بارگذاری رسانه و صفحات پنل را در staging واقعی بررسی کنید.
